# 4 — Verification, Maintenance, and Preservation

The native Smaug build is intended to remain reproducible through explicit
source contracts rather than an assertion that a 2026 binary will execute
unchanged centuries later.

## Verification

```sh
cd smaug
make clean
make check
make
make dream
```

`make check` is the compile-only gate. CI should exercise both C and C++
compilers. The portable system store remains independent of a mandatory MySQL
client.

## Firecaster verification

The Firecaster model has three separable concerns:

1. **Eligibility** — upper modeled Strain limit.
2. **Comparison** — known dice versus opposing known dice, with modeled
   spellcaster count contributing to Good-Odds.
3. **Resolution** — `2D8 + 48 + (Perch Rank × 72)` Hit Dice.

These are simulation values and should be recorded in evidence output. They do
not grant host-system capability.

## Native gate verification

The native gate standards are verified by the same C++ syntax gate. The critical
invariants are:

1. privilege is bounded to the modeled 3–7 range;
2. provenance is mandatory;
3. the protected target must be explicit;
4. only Firecaster and BreathWeapon are accepted effect tokens;
5. effects remain simulation-only;
6. Herald output is observational and cannot grant authority.

The existing `SmaugAdminGate` remains the final protected-path boundary. The new
standards layer is an additional validation surface, not a bypass.

## Preservation

Preserve source, specifications, build recipes, schemas, evidence formats,
compiler assumptions, and migration notes. Prefer deterministic identifiers and
bounded data structures. Future maintainers should be able to rebuild the system
from source and migrate stored records when operating systems or ABIs change.

## Current feature record

The documentation set now covers Smaug/smaug, Overtine, Companion AI, Emerald,
Wanderer, Smite, Firecaster Strain and Good-Odds, Admin gates, Player/Overtine
inputs, Detail/Treasure, Dream lifecycle, the native gate standards, and Herald
observability.

A 500-year horizon is treated as a preservation objective, not a guarantee that
present-day binaries, operating systems, or hardware will still exist.
