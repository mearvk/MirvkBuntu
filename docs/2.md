# 2 — Architecture and Operating Model

Smaug is organized as cooperating, bounded layers.

```text
Player ────────┐
               ├→ Input → Companion/AI → Castle/INCLARE → Smite → Record
Overtine ──────┘                 │
                                 ├→ Emerald
                                 ├→ Wanderer
                                 └→ Firecaster (simulation)

System → OS awareness → inspection store → evidence

Dream → bounded restorative lifecycle → Ready
```

Overtine supplies stable companion calls through Constantine, Reign, Better-Be,
and Better-Companion-Be. The Companion AI provides Emerald Strike Pick,
Wanderer Mid Pick, and Pre-Strike Thoughtfulness as bounded advisory functions.

The native C and C++ layers share the public Smaug decision contract. C-callable
entry points permit small, stable integrations while C++ provides richer state
models.

## Geometry and limits

The Overtine model uses 3D axial/co-axial state and permits no more than five
modeled dimensions, 1,112 strand signatures, and 1,112,221 modeled coil lengths.
These are implementation bounds, not preallocation requirements.

## Native gate and Herald path

The system-facing path is now explicit:

```text
input
  → normalize
  → provenance
  → validate
  → assess
  → authorize
  → simulate
  → record / Herald
```

`SmaugAdminGate` is the protected administrative boundary. `SmaugGateStandards`
adds bounded stage, privilege, provenance, target, and effect validation.
`SmaugHerald` announces the resulting disposition and retains a bounded event
history for inspection. None of these components owns or mutates protected
filesystem state.

The administrative privilege model is deliberately bounded to levels 3 through
7. Recognized administrative effects are Firecaster and BreathWeapon, and both
remain simulation-only tokens.
